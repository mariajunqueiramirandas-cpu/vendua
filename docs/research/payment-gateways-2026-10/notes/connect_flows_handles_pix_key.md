# "Type an account name" payment connections (handle / Pix key), Brazil

Research date / access date for every URL below: 2026-10-02. Scope: ways a platform can take shopper payments into a merchant's own account when the merchant only enters an identifier (no OAuth, no pasted secret keys). Fees only noted incidentally.

Legend: [P] = primary source read directly (page or PDF text); [S] = secondary / search-result summary, treat as lower confidence; [?] = could not confirm.

## 1. InfinitePay Checkout Integrado (the handle model)

How it works [P]

- `POST https://api.checkout.infinitepay.io/links` with `handle` (the merchant's InfiniteTag, no leading `$`), `items[]` (quantity, price in cents, description), optional `order_nsu`, `redirect_url`, `webhook_url`, `customer`, `address`. Returns a hosted checkout link (Pix or card up to 12x). The example curl on the product page shows no auth header. Source: https://www.infinitepay.io/checkout-documentacao and https://www.infinitepay.io/checkout (fetched raw HTML).
- Status check: `POST https://api.checkout.infinitepay.io/payment_check` with `handle`, `order_nsu`, `transaction_nsu`, `slug`; response has `success`, `paid`, `amount`, `paid_amount`, `installments`, `capture_method`. Same doc.
- Redirect back to `redirect_url` carries `receipt_url`, `order_nsu`, `slug`, `capture_method`, `transaction_nsu`. Same doc.
- Webhook (sent when payment approved): body `invoice_slug, amount, paid_amount, installments, capture_method, transaction_nsu, order_nsu, receipt_url, items`. Merchant must answer 200 (preferably <1 s); 400 triggers retry. `webhook_url` can be set per link (dynamic). Same doc + help article https://ajuda.infinitepay.io/pt-BR/articles/10766888-como-usar-o-checkout-integrado-da-infinitepay (dated 2026-07-22).
- Merchant has to enable "Checkout Integrado" in the InfinitePay app (Vendas > Checkout > Configurações), per the same help article [P].
- Doc tips: "sempre valide se o order_nsu corresponde a um pedido real", "guarde o transaction_nsu"; mentions testing "no ambiente de desenvolvimento" but documents none [P].
- Pix is advertised as zero fee with instant settlement; card 2.69%-4.2% by plan (incidental) https://www.infinitepay.io/blog/integracao-infinitepay [P, page dated 2026-09-21].
- Settlement: directly in the merchant's InfinitePay account (instant or D+1); Venduá never touches funds. [P: product pages]

Payment confirmation: automatic (webhook + `payment_check`). The webhook has NO documented signature or secret; the only authenticity check available is to call `payment_check` yourself with the handle + `transaction_nsu` + `slug` (and compare `amount`/`paid_amount`, `order_nsu`). [P: docs show no signature; inference that payment_check is the defence]

Ownership verification: none found. The docs only say the handle "é obrigatória para identificar sua conta". No test charge, callback, OTP or token proving the caller owns the tag was documented. A community WooCommerce plugin mentions an optional Bearer token "from the developer panel for accounts requiring authentication" https://github.com/AlfaStage/wc-infinitepay [S, plugin README; not in official docs]. So a mistyped or someone else's handle would create links that pay that other person. A test payment does NOT prove ownership: the payer already gets the `receipt_url` and `transaction_nsu` through the redirect, so someone using another person's handle can pay a test link and submit those values without access to the recipient's account. Ownership stays unresolved until InfinitePay offers an authenticated account-binding mechanism; ask parcerias@cloudwalk.io. Until then a handle integration risks routing shoppers' money to the wrong account.

Not documented / [?]: refunds via API (docs and help article are silent; refunds appear to be done in the merchant's app, see https://www.infinitepay.io/blog/estorno-de-debito [S]), sandbox (none documented), rate limits (none documented), partner/platform program (the developer page lists InfiniteTap and Checkout Integrado, contact parcerias@cloudwalk.io, "nenhum programa formal", https://www.infinitepay.io/desenvolvedores [P]). Terms of Use and Contrato de Afiliação (https://www.infinitepay.io/legal/termos-de-uso, https://www.infinitepay.io/legal/contrato-de-afiliacao) were grepped: no clause on handle use by third-party platforms or on API terms. Legal risk for a platform generating links on behalf of merchants is therefore unaddressed; asking parcerias@cloudwalk.io would be the way to get written permission. Search snippets claimed a "new official infrastructure from 2026-06-01"; the help article does not say so [S, unconfirmed]. "Jim.com"/JIM is described on InfinitePay's nav as "assistente financeiro do negócio"; no public payment API found [?].

## 3. Plain Pix key + BR Code (no PSP integration)

Facts from BCB Manual de Padrões para Iniciação do Pix v2.10.0 (https://www.bcb.gov.br/content/estabilidadefinanceira/pix/Regulamento_Pix/II_ManualdePadroesparaIniciacaodoPix.pdf, section 2.6, text extracted from PDF) [P]:

- Static QR carries: Pix key (required), amount (optional, BR Code ID 54), free text `infoAdicional` (optional, <= 72 chars, competes with key for 99-char template), txid (BR Code ID 62-05), optional fss (Pix Saque). Merchant name is mandatory in EMV/BR Code.
- txid on static QR: EMV 62-05 Reference Label, max 25 chars, alphanumeric `[a-zA-Z0-9]`. "Quando em efeito, deve ser utilizado para conciliar pagamentos"; the payer's PSP must "retransmitir intacto" it in the payment order so the receiver can correlate. If not used, value must be `***`. So txid is standard on static QR, but unlike dynamic charges the BCB does not issue/guarantee uniqueness; the generator must manage ids (uniqueness point from a secondary source, https://aurumlegacy.com.br/blog/pix-qr-code-dinamico-estatico [S]; manual itself only says what is quoted).
- No Pix Troco on static QR; dynamic QR gives reconciliation, expiry, amount-locked charge via PSP API (manual sec. 2.4.2).

What the payer sees (BCB Requisitos Mínimos para a Experiência do Usuário v7.3; v7.4 effective 2027-03-01) https://www.bcb.gov.br/content/estabilidadefinanceira/pix/Regulamento_Pix/IV_RequisitosMinimosparaExperienciadoUsuario.pdf [P]:

- Paying a static QR: before confirming, payer's app must show DICT data for the receiver: name, CPF masked / CNPJ unmasked, and the amount if in the QR; CNPJ shows Nome Fantasia if it exists, else Razão Social; there is a cancel option "para diminuir devoluções equivocadas". Agency/account are not shown.
- Paying by key: same data (name, masked CPF/CNPJ, key) must be returned for conferência.
- Implication: the key holder's DICT name is shown to the shopper by their own bank, not to Venduá, and the QR's merchant-name field is merchant-supplied, not verified.

Automatic confirmation: none from the BR Code itself. The platform does not control the key, so it receives nothing. Options:

1. Merchant confirms manually in their bank app (Goomer "Pix Manual": merchant enters chave + account name and "precisará confirmar o pagamento no app do banco da chave" https://ajuda.goomer.com.br/goomergo/painel/goomergo/formas-de-pagamento/pix-manual [P]; Fabi Delivery: random key only, customer copies key, merchant confirms https://ajuda.fabapp.com/pt-br/article/pagamento-via-pix-validacao-manual-fabi-delivery-139ctwp/ [S]).
2. Merchant's bank/PSP webhook relayed by a confirmation service: PixConfirm (https://www.pixconfirm.com.br/ [P marketing page]) claims webhook confirmation "no segundo", does not hold funds, supported banks Mercado Pago, Asaas, BB, Sicredi, Sicoob, PagSeguro, Inter, C6, Stripe, Bradesco, Caixa (Itaú, Santander, Nubank coming). It needs the merchant to connect their bank/gateway, which almost certainly means credentials/keys [inference]; fails the "no secrets" constraint.
3. Open Finance data sharing (aggregators such as Pluggy): shopper-independent; merchant authorises sharing in their bank app (OAuth-style consent, up to 12 months; PJ accounts often need several approvers). Transactions include Pix details (payer, institution, end-to-end ID) and a stable transaction id; webhooks with retry exist https://www.pluggy.ai/blog/api-extrato-bancario-erp-sistema-gestao (2026-07) [P]. Not "type a name": it is a consent flow, and latency is not documented [?]. Whether txid is exposed is [?].
4. Notification/e-mail parsing hacks (e.g. https://github.com/tzanella/nubank-api-pix) [S]; fragile, not recommended.

Fraud / MED: MED does not cover typing the wrong Pix key (https://blog.pagbank.com.br/mecanismo-especial-de-devolucao-pix, updated 2026-09-04 [P]; also meutudo/iugu summaries [S]). Instrução Normativa BCB 766 (in force 2026-09-01) extended to 80 days the period to contest a MED refund and targets the "double return" scam; merchants should refund through the app's linked-refund function [P per PagBank article]. For the handle/key-typo risk: shopper money would land with a third party and be unrecoverable via MED except by voluntary return.

## 4. Open Finance payment initiation (ITP): "pays into a key/account the platform doesn't hold, with automatic confirmation"

- Open Finance Brasil payment-initiation flow: shopper consents in their own bank (or Jornada Sem Redirecionamento, mandatory for account holders from 2026); an ITP (payment initiator authorised by BCB; not required to be a Pix participant) instructs the shopper's bank to pay the creditor; ITP notifies the merchant in real time; the vendor describes it as "sem chargeback" https://azify.com/en/blog/itp-open-finance (2026-10-01) [S]. That means no card-style chargeback, not irrevocable: an ITP-initiated Pix hit by fraud, coercion or institution error can still be blocked and returned through MED, so the flow must handle reversals. API payload carries creditor account (ispb, issuer, number, accountType) and optionally `proxy` + `localInstrument: DICT` (key) [S, search snippet of OF schema; verify at https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1053884657 which I could not read fully].
- Volume is small: 64.5 million payments / R$ 15.3 bn in 2025, under 0.1% of Pix https://www.letsmoney.com.br/noticias/pix-open-finance-salta-8-vezes-2025/ [S]. Providers named: Iniciador, Pagar.me, Pluggy, Sensedia, iFood Pago.
- Relevance: Venduá would need to be (or contract) an ITP, and the ITP's merchant onboarding likely requires KYC of the merchant; whether it accepts an arbitrary key without merchant contract is [?]. This is the only route found that gives automatic confirmation on a key the platform does not control without merchant-side secrets, but via a regulated third party.

## 5. DICT lookup before paying / ownership checks

- Only a Pix participant (PSP) can query DICT; vendors such as Celcoin expose it as "Consultar Chaves Pix Externa (DICT)": returns holder name/Razão Social, masked CPF/CNPJ, ISPB, branch, masked account, account type, an end-to-end id valid 12 h; requires bearer auth and `PayerID` = integrating institution's CNPJ; DICT rate limiting uses token buckets "to prevent read attacks" https://developers.celcoin.com.br/docs/consultar-chaves-pix-externa-dict [P]. Venduá cannot do this alone without a PSP contract; not a free primitive. It would show "who owns this key" so the merchant can confirm the name/CNPJ matches the store's CNPJ at setup.
- Penny test: platform shows a unique amount (e.g. R$ 0,01 + random cents or a txid) via static QR or via the handle link; merchant pays it from another account and the platform must see the confirmation. This proves only that a payment reached the handle or key, not that the person configuring it controls that account: the payer sees the receipt too. It catches typos, not someone entering another person's handle. With a bare Pix key it also needs one of the confirmation channels in section 3.
- OTP in the provider app: none found for InfinitePay handles. Nubank's NuPay uses OAuth2 + CIBA/OTP (kmee, above) but that is the OAuth-class flow the brief excludes.

## 6. How food/delivery platforms use "Pix na chave" vs integrated

- Goomer: "Pix Manual" (chave + account name, merchant confirms in bank app) vs integrated online payment (card/Pix, order enters kitchen only after system validation; also lists "link Mercado Pago") https://ajuda.goomer.com.br/goomergo/painel/goomergo/formas-de-pagamento/pix-manual , https://goomer.com.br/blog/pagamento-online-delivery [P/S].
- Anota AI: help center names partners Tuna and iFood Pago for online payment https://anota.ai/ajuda/duvidas-frequentes/ [P]; blog describes "Pix Automatizado" where the merchant registers a Pix key, the attendant sends a link and the order appears only after payment (2022, updated 2023) https://anota.ai/blog/pagamento-via-pix/ [P]; a search snippet says setup requires the key's account to share CPF/CNPJ with the company plus legal-representative data and payment within 5 min https://anota.ai/ajuda/ [S]. Exact PSP and who holds funds not disclosed [?]. The CPF/CNPJ-match requirement is a useful ownership check pattern (hold-and-match against KYC data) but implies a PSP in the middle.
- Cardápio Web, iFood own, Delivery Much, WhatsApp tools: not confirmed in this session [?]. Related: Fabi Delivery (random key, manual), Consumer/MenuDino (guide exists, not read).
- Woovi (OpenPix): collects then settles to the merchant's Pix key/account; requires the account CNPJ to match the CNPJ registered at Woovi https://ajuda.woovi.com/hc/duvidas-frequentes/articles/consigo-receber-pix-com-api-no-nubank [P]. Money transits the PSP, so not "direct" in Venduá's sense; included as an example of CNPJ-match ownership checking.
